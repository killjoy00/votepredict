# 2027 bounded daily collection — implementation, not activation

This is the first direct GitHub/Neon worker for the 95th Legislature. It reuses the tested live bill catalog and status importers and adds **session-scoped** initial text retrieval, rather than calling the historical backfill across every biennium. No model fitting, Quick scheduling, vote ingestion, outcome reconciliation or P8 daily capture is authorized by this workflow.

- Default workflow mode is a credential-free plan; no scheduled/push/post-deploy trigger. A later one-shot live run requires an explicitly approved main revision, the protected collection environment, configured least-privileged collector identity and fingerprint, a green exact-main CI check, Jan 12 2027 or later (Chicago date), and the existing 37-migration ledger. The script fails closed for database owner/superuser, write privileges on forecast/vote/roster/session tables, or mutation rights on the content archive. The role and credential are **not provisioned** in this change; use the existing protected Neon credential deployment path to configure a restricted role once separately authorized. Never use an owner connection or fall back to Vercel.
- One single-worker GitHub concurrency group plus PostgreSQL advisory lock; a successful batch cannot be repeated the same Chicago day, and at most two starts/day (failure/interruption retry only). Initial pilot limits: up to 32 catalog requests, 40 status attempts, 20 initial documents (at most 60 HTTP attempts), 132 total requests, 2 MiB per response, 32 MiB/run, eight-minute network deadline, 12-minute job timeout. These are conservative proposed pilot limits, not evidence of daily coverage or an approved spend budget.
- The existing source functions use a scoped async wrapper only inside this worker. It allows exact official 95th-session catalog/status/initial-version URLs, rejects credentials and redirects, reads bounded response bytes before parsing, and synchronously archives each received body and acquisition receipt. Receipt contains URL, media type, HTTP status, observation clock, size/hash and run identity. Byte preservation refers to the HTTP entity returned by fetch after transport decoding, not compressed wire bytes. It uses existing migration 0037 append-only SHA-256-checked content blobs. Raw bytes and receipt commit together and are verified on readback. No new database migration or service. Repeated identical bodies deduplicate but each actual observation is distinct. A body that cannot be archived is not admitted to the importer.
- A durable started record and final report are append-only content blobs; GitHub Actions publishes a compact report and warning annotations, including raw-body receipt hashes, zero or regressed catalog yield, failed requests, missing archive attempts, stale/unobserved status and missing initial text. A killed runner leaves its start visible; absence of a terminal record is not success. The exact original source bodies are retained in Neon, not in expiring job artifacts. This is database-level retention, not independently administered WORM. Separate external archival/seal policy and live alert/heartbeat delivery remain launch gates.

A successful batch means only bounded collection worked, not that every introduced bill was captured daily. If the roster isn't active or official catalog is empty/regresses, the worker refuses or records partial failure. The first actual nonempty source response needs verification; no assumption of official universe completeness is made. As introduced bills grow, revisit the pilot limits with actual source/compute usage; use no expensive automatic historical requests. Remaining: authenticated calendar and independent denominator, current-version text/vote/evidence adapters and retention, heartbeat delivery, role grants, budget, one controlled canary and explicit single-scheduler approval. Keep #732 pause and #287/#310 frozen gates. No live collection, Vercel request, production database change or new recurring costs in this PR.

The regression suite also creates an isolated schema in the CI disposable PostgreSQL instance using the exact migration-0037 content-store DDL. It tests original-byte readback (including a BOM), deduplication, distinct acquisition receipts, acceptance-clock agreement, rollback of invalid receipts, and immutable update/delete/truncate rejection. Each run also reports the previous Chicago day's durable heartbeat: not due, missing, interrupted, partial failure, or completed bounded batch. No independent heartbeat job or external alert delivery is enabled yet.

## Current-version collection extension

The worker also captures up to 20 missing current official engrossments per run (20 further GETs, total ceiling 152; original byte and runtime budgets unchanged). Only fresh successfully observed current status, a published numbered official version with matching bill/session/ordinal URL and matching DB version is eligible. The raw HTML acquisition receipt is checked against the immutable blob, parsed text is separately hashed and inserted into the existing append-only forecast text observation store at its **actual** acquisition time, and a retained binding records the raw receipt, version, parsed hash and observation ID. The transaction rechecks the current status and version; conflicting existing text is not rewritten. A failed bill advances the current-text attempt order and appears in the failure and backlog report. Earlier version observations are never changed. Existing current-stage forecast creation remains disabled; future forecast launch must independently require a fresh matching current-version observation. The new role additionally needs INSERT/SELECT-only access to forecast_bill_text_observations. Real 2027 official version URL and HTML shapes remain to be verified at first publication; URL scope is intentionally fail-closed.
