## The known problem, before this change

[Protected read-only V47 census](https://github.com/killjoy00/votepredict/actions/runs/38791984923) measured **0/830** exact original viewer URL/PDF whole-body SHA matches inside the existing \`source_documents\` table. The existing bulk finance evidence covers **296/362** indexed candidate-year pairs; it is not an exact version match. Existing eligible context **58,555** stored finance evidence copies; **0** had a provable original report-version ID and **50,173** were filing-date-derived. Thus **0** legacy eligible copies were *actually revalidated* against the V46 report-version dates. Contribution, expenditure and independent-expenditure categories were correctly separated in V47 and remain separated here.

## What V48 does

1. **Persist original government document identities, without pretending finance row lineage.** New table \`cfb_official_senate_pdf_versions\` contains one row for each of the 830 government-indexed report-version IDs, 813 distinct whole PDF SHA-256 fingerprints, exact official viewer URLs, registration/year, original body length, original printed Board-received date when present, documented statutory release floor, selected practical availability estimate, observation date, dating rule and confidence. It stores **no PDF bodies, donor/vendor names, transaction amounts or member financial records**. Same-body amendment aliases stay separate document identities.
2. **Verify the persistent corpus in Neon.** Bounded idempotent import uses \`ON CONFLICT DO NOTHING\` then rejects any discrepancy: exact versions, full-body SHA and size, original date fields, confidence and the government viewer URL must all match the immutable checked-in original sources; no extra registry rows are permitted. The migration has an independent immutable schema-ledger checksum check. Only the new registry and its one migration-ledger entry may be modified, never \`source_documents\`, \`evidence_items\`, model or forecasts.
3. **Revalidate existing stored finance-eligibility metadata as a diagnostic census.** The protected query examines previously labeled \`asOfEligible=true\` evidence only, separately for candidate contributions, candidate expenditures, independent expenditures and classification mismatches. An exact source-version reference, if one exists in evidence metadata, must match registration **and** filing year. For candidate-year-only matches, compare stored timestamps to the **earliest possible** statutory release and V46 estimated public-availability day across candidate report versions. A timestamp earlier than every possible candidate version is a genuine *triage flag*. A timestamp after a plausible version's date is **not** proof the specific transaction appears in that PDF. Multiple candidate PDFs remain **ambiguous**, and independent expenditure evidence cannot inherit candidate principal PDFs. Output is safe year/category/scope integer counts only.

## What V48 does NOT do

- Does **not** attach arbitrary candidate-year PDF version IDs to bulk \`evidence_items\`; registration/year alone cannot authenticate individual transaction inclusion or amendment membership.
- Does **not** promote, rewrite, disable or delete \`asOfEligible\`, \`published_at\` or legacy flags: v46 dates by themselves are estimated timing context, not row-to-PDF containment proof. Even a sole indexed PDF in a candidate-year does not verify that the *transaction* is in it.
- Does **not** claim an archived historical public-by time, full legal filing-duty denominator, certified complete financial row import, or verification of PAC/party/non-candidate independent expenditure transaction contents.
- Does **not** touch serving, forecast training, historical prediction outcomes, Vercel or schedulers. Other #864 committee, campaign-site and media work remains outside this change.

## How it runs safely without new credentials

The PR's zero-secret CI validates every source SHA and date, runs synthetic controlled transaction/rollback tests, applies the migration to **ephemeral localhost PostgreSQL**, then executes the insert, exact integrity comparison and eligibility SQL inside a local rollback. After review and squash merge to main with the exact \`SENATE_864_CFB_PDF_LINK_REVALIDATE_V48\` marker, a new first-attempt **independent no-secret preflight** reruns local database tests, \`npm run check\` and production dependency audit. If and only if this passes, the repository's **existing** \`secrets.NEON_API_KEY\` and \`vars.VOTEPREDICT_NEON_PROJECT_ID\` in the protected \`evidence-readonly-sandbox\` environment target the **existing independently selected default VotePredict Neon branch**, selecting its **existing primary**, with a bounded single serializable transaction. No new Neon secret, project, branch, username or manual owner action required. The transaction verifies the preexisting migration checksums, adds only the new registry and migration entry, checks 830/830 exact stored parity and emits aggregate eligible-date counts, then commits. All partial failures roll back. GitHub's separate keyless job summarizes sanitized aggregate-only findings to [issue #864](https://github.com/killjoy00/votepredict/issues/864).
